---
title: "Orchestrator"
description: "A singleton headed agent session that dispatches ready cards to coding agents"
---

The orchestrator is a single, long-lived **headed Claude Code** session that
dispatches work on your behalf. It does exactly one thing: on a recurring loop it
finds cards that are ready to run, picks which coding agent to start for each, and
starts it through the Vibe Kanban MCP tools. It does not monitor, drive, review,
merge, or answer questions for those agents — once a card is dispatched, the coding
agent owns it end to end and you handle delivery.

## What makes it special

- **Singleton.** There is at most one active orchestrator at a time. Requesting a
  new one reuses the existing session rather than spawning a second.
- **Repo-independent.** It does not belong to any one project. It runs from a
  fixed `~/.vibe-kanban/orchestrator` folder, so it can reason across every
  project on the board.
- **Headed.** It runs as an interactive Claude Code session (a detached tmux
  session), so you can attach to it, watch it think, and send it input — the same
  controls as any headed workspace.

## Spawning it

Spawn the orchestrator from the app. Spawning is **idempotent**: if an
orchestrator is already running, the action returns the existing session instead
of creating a new one. The app launches it as the `vibe-kanban-indie:orchestrator`
agent on a `/loop` timer (every 5 minutes), so its behaviour lives in the plugin,
not in the app — each tick is one dispatch sweep of the board.

<Note>
Because it runs from `~/.vibe-kanban/orchestrator` rather than a project worktree,
the orchestrator has no working repository of its own. It acts on projects by
calling MCP tools, not by editing files directly.
</Note>

## How it acts on the board

The orchestrator uses the Vibe Kanban MCP server in **global** mode, which gives
it board-wide tools to:

- List and read issues, repositories, and workspaces (to find ready cards and avoid
  starting one that already has a workspace)
- Resolve which coding agent to run — the agent pinned in the card's pipeline, or
  your last-used/default agent configuration when the card pins none
- Start a workspace and dispatch one coding agent per ready card, then move the card
  to In Progress

Everything after dispatch — monitoring, approvals, reviews, merges, and answering an
agent's questions — is outside the orchestrator's scope by design. The coding agent
drives its own pipeline, and you deliver the result.

## Staying in control

You remain the final authority. At any time you can:

- Attach to the orchestrator's tmux session to watch or steer it
- Override any decision from the [TUI cockpit](/cockpit/tui)
- Reply directly in Telegram
