Indie can take a card from a rough brief to a merged change with very little
hands-on dispatch. It does this with three building blocks: **per-card pipelines**
that declare what should happen, an **agent crew** that performs each stage, and an
**orchestrator** that schedules the work. You stay in control — you choose which
stages a card runs, **Wait for approval** is the stage that pauses a pipeline for
your decision, and you can override from the [TUI](/cockpit/tui) or Telegram at any
time.

## Per-card pipelines

When you create an issue, you choose its **pipeline** — the ordered stages that
should run — with checkboxes. The selections are appended to the card description,
so the pipeline travels with the card. Each stage is toggleable; a pipeline ships
each stage on or off by default (its recommended setting).

The built-in stages are:

| Stage | What it does |
|---|---|
| Orchestrate (auto-drive) | Hand the card to the orchestrator to drive end to end |
| Create spec | Turn the brief into a development-ready spec (`SPEC.md`) |
| Create plan | Turn the spec into a concrete implementation plan (`IMPLEMENTATION_PLAN.md`) |
| Review plan | Review the plan before any code is written (delegated to Codex) |
| Codex plan review | Independently review the implementation plan with Codex before any code is written (Async Opus / Async Sonnet / Async Fable, on by default) |
| Wait for approval | Pause and wait for your decision before continuing |
| Review via Codex | Independently review the change's diff with Codex once code is written |
| Update documentation | Update the docs the change affects |
| Merge to base | Squash-merge the workspace branch into its base — the agent does this itself; listing the stage is the authorisation |
| Open pull request | Open a GitHub pull request |

<Note>
The stage catalogue is config-driven. The default order puts **Orchestrate
(auto-drive)** first; `Wait for approval` follows `Review plan`, and `Update
documentation` follows `Review via Codex`. In the **Async Opus**, **Async
Sonnet**, and **Async Fable** pipelines, the ordering is spec → plan →
**Codex plan review** → coder stage → **Review via Codex** (the shared
code-review stage): the plan is independently reviewed before any code is
written, and the diff review runs only after the coder stage. All three
pipelines review with Codex only — there is no Fable diff-review stage.
</Note>

## The Async pipelines

All three Async pipelines fan work out to subagents instead of doing it in the
main loop: an Opus main loop coordinates, verifies, and reviews, while separate
subagents write the spec, the plan, and the code. They differ in which model does
that subagent work, trading cost for thoroughness:

| Stage | Async Opus | Async Sonnet | Async Fable |
|---|---|---|---|
| Spec | Opus subagent (`vibe-kanban-indie:product`) | Sonnet subagent (`vibe-kanban-indie:product`) | Fable subagent (`vibe-kanban-indie:product`) — **heavy**, on by default |
| Plan | Opus subagent (`vibe-kanban-indie:planner`) | Sonnet subagent (`vibe-kanban-indie:planner`) | Fable subagent (`vibe-kanban-indie:planner`) — **heavy**, on by default |
| Codex plan review | On by default | On by default | On by default |
| Code | Sonnet subagent (`vibe-kanban-indie:coder`) | Sonnet subagent (`vibe-kanban-indie:coder`) | Opus subagent (`vibe-kanban-indie:coder`) |
| Review via Codex | Off by default | Off by default | Off by default |
| Merge to base | On by default | On by default | On by default |

All three pipelines are Codex-only for review — none has a Fable diff-review
stage. The plan is always reviewed; the **diff** review is off by default, so tick
**Review via Codex** on a card when you want one. **Merge to base** is on by
default: once the stage is listed, the agent squash-merges the card's branch into
its base itself, without waiting for a go-ahead. Add a **Wait for approval** stage
when you want to gate that. Run any of them with a Claude Code (Opus) execution
agent, so the main loop has the model budget to coordinate the fan-out and verify
each subagent's work.

<Note>
Async Fable's spec and plan stages are marked `heavy = true` **and** default
to ticked — a deliberate exception to the usual "heavy starts unticked"
convention (see below). Choosing Async Fable at all is the opt-in to the
extra cost; the heavy badge stays on to keep that cost visible, not to gate
it a second time.
</Note>

<Note>
Bundled pipeline files are seeded once per filename and tracked in a
`.seed-manifest.json` file inside `~/.vibe-kanban/pipelines/` (invisible to
the Settings pipeline list). When a bundled pipeline gains a new stage, or a
new pipeline ships, an existing pipelines directory picks up exactly the new
file or stage automatically on the next backend start — you no longer need to
reset a pipeline by hand to pick up changes shipped after your install. Edits
and deletions stay sticky either way: once a filename has been seeded, it is
never silently overwritten or resurrected. The retired `async.toml` (replaced
by Async Sonnet and Async Fable) is removed automatically the same way, but
only when its contents still match a shipped version byte-for-byte; an edited
copy of it is left alone as your own custom pipeline.
</Note>

A stage can also be marked `heavy = true` in its pipeline TOML — a
resource-intensive stage that the New Issue dialog shows with a small "heavy"
badge. By convention a heavy stage starts unticked, so you opt into the extra
cost explicitly; Async Fable's spec and plan stages are the one bundled
exception, since picking that pipeline is itself the opt-in.

## The agent crew

Each stage is performed by a focused agent. They are separate roles so that the
agent writing the spec is not the one writing the code, which keeps each step
honest.

<CardGroup cols={2}>
  <Card title="Product" icon="clipboard-list">
    Turns a rough brief into a structured, development-ready card — the *what* and
    the acceptance criteria.
  </Card>
  <Card title="Planner" icon="diagram-project">
    Turns a specced card into a concrete, file-grounded `IMPLEMENTATION_PLAN.md` —
    the *how*.
  </Card>
  <Card title="Orchestrator" icon="robot" href="/cockpit/orchestrator">
    A singleton headed session that dispatches one coding agent per ready card on a
    recurring loop.
  </Card>
  <Card title="Decider" icon="circle-question">
    Answers an agent's stale questionnaire after a grace window, using the card,
    spec, and plan as context.
  </Card>
</CardGroup>

<Note>
The crew is delivered as the `vibe-kanban-indie` Claude Code plugin, which links to
the `sombrax-codex` plugin for the review stages and the `sombrax-telegram` plugin
for fan-out. See [Claude Code plugins & skills](/integrations/claude-code-plugins).
</Note>

The Product agent can also attach a pipeline when it files a card — say "create
a card and put it through Async Fable" and it reads the pipelines directly from
`~/.vibe-kanban/pipelines/*.toml` and composes the same `## Pipeline` block into
the card description that the New Issue dialog would, defaulting to each
pipeline's `default_enabled` stages unless you name specific ones. It only adds
the Orchestrate stage when you explicitly ask for the card to be executed or
auto-driven — Product itself never starts a workspace. See the
`product-manager` skill's "Attaching a pipeline" section for the exact format.

## Spec and plan artifacts

The spec and plan are real files materialised at the workspace root —
`SPEC.md` and `IMPLEMENTATION_PLAN.md` — so each subsequent stage reads the
previous stage's output the same way a human reviewer would. The
[Generate a spec](/cockpit/spec-intake) flow can also produce a spec directly from
the New Issue dialog before any workspace exists.

## How it runs

The orchestrator runs on a `/loop` timer. On each sweep it:

1. Finds cards that are ready to run but have no workspace.
2. Resolves which coding agent to use — the one pinned in the card's pipeline, or
   your last-used or default configuration.
3. Starts one coding agent per ready card and moves the card to In Progress.

By default the coding agent then owns its card's pipeline end to end. You can opt
into orchestrator **directives** at spawn time — auto-unblock routine approvals,
auto-answer stale questions (via the decider), and Telegram fan-out — each as a
simple flag whose behaviour lives in the agent's instructions, not the app.

## Staying in control

Automation never removes the human. A `Wait for approval` stage pauses the
pipeline for your decision, escalations surface in the TUI and Telegram, and you
can attach to any headed session to watch or steer it.
